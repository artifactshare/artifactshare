# 発見経路と一覧の制限値を分けて設計する

- Status: Accepted
- Date: 2026-08-24

## Context

「最近見たファイルへ戻る」タスクの walkthrough では、対象ファイルを直接開けば Viewer は正しく動作した。
しかし、利用者が出発する Home では対象を候補から見つけられず、直接遷移する検証ではタスクの断絶を見逃した。
walkthrough は、開始位置で全件導線の存在を確認し、全件一覧に表示された対象をクリックする操作へ修正した。

Home の候補一覧と全件一覧は、同じファイル行を使っていても役割が異なる。
Home は次の行動を選ぶための要約であり、全件一覧は要約から漏れた対象を探し直す回復先である。
要約用の表示件数を全件一覧へ流用すると、回復先まで同じ範囲に切り詰められる。

## Decision

操作の存在と、利用者の出発位置からの発見可能性を別々に確認する。
リンク先へ直接遷移する検証は、遷移先の成立だけを証明する。
タスクの成立を検証するときは、台帳の開始状態から画面上の手がかりを選び、目的の状態まで操作する。

一覧の制限値は、表示面の役割と一緒に定義する。
既存の値を流用できるのは、利用者の目的、選択範囲、並び順、回復経路が同じ場合に限る。
要約、検索結果、全件一覧、ページ単位の件数は、同じデータを表示していても別の役割として扱う。

## 批評で確認する問い

- 利用者はタスクの開始位置で、次の操作をどの手がかりから見つけるか。
- walkthrough はその手がかりを実際に選んでいるか。それともリンク先へ直接遷移していないか。
- 表示件数から漏れた対象へ進む全件導線、検索、ページ移動などの回復経路があるか。
- 流用する制限値の元と適用先は、利用者の目的と一覧の役割が同じか。
- 制限値を超える fixture でも、目的の対象を発見してタスクを完了できるか。

## Consequences

画面に操作が実装されているだけでは、タスク完了の根拠にしない。
walkthrough と批評は、開始位置からの探索と、制限を超えた場合の回復を証拠に含める。

この2原則のための専用ライブラリ、独自ページ形式、機械検査は追加しない。
現時点では人間と批評 agent が適用先の役割を判断する。
