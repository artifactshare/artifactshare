# Controlled Review

このスキルを読んだ親が統括する。組み込みの `/code-review` や `codex review` へ処理を移さず、ここで定義した依頼文を各レビュー役へ直接渡す。Claude Code でも `context: fork` を設定しない。

統括役が対象、作業条件、観点の割り当て、モデルと effort、実行量、指摘の採否を決める。探索役と検証役は指定された仕事だけを返す。モデル配置や既存の公開・レビューゲートを、このスキルから変更しない。

## 1. 今回の作業条件を固定する

ユーザーと呼び出し元の指定を引き継ぎ、適用されるリポジトリ指示を読む。[作業条件のひな形](references/context.md)に沿って、以下を1本のUTF-8 Markdownへまとめる。既存の同等な文書があれば使い、単に形式を合わせるための台帳を増やさない。

- 対象リポジトリ、比較元・対象の固定SHA、対象パス、固定した差分の保存先または固定SHA間の差分を読むGit操作、base/head双方のコードを読める経路。明示された未コミット変更は、差分と対象ファイルの内容を固定したスナップショットで識別する。
- 変更目的、受け入れ基準、対象外、適用規約、検証済みの事実と未確認事項。
- 既存指摘のID・処分・理由。初回なら「既存指摘なし」と明記する。修正後のレビューで処分を空に戻さない。
- 実行する観点、各役のモデルと effort、並列数、候補数・追加呼び出し・再試行・時間の上限、許可する検証。

指定がなければ、観点は後述の8つ、各探索役の候補は最大6件、並列数は利用可能枠に親の分を残した数とする。モデル・effortはセッションとリポジトリの明示設定を使い、なければ親と同じ設定を使う。親の設定が不明なら継承と記録し、推測した別モデルに置き換えない。実行量の上限は対象規模に応じて統括が開始前に示す。既定から解決した値も含め、実際に使う値を作業条件へ明記する。既に指定・承認された条件は聞き直さない。

比較元を省略された場合は既定ブランチとのmerge-baseを確認する。push先のupstreamを無条件に比較元にしない。対象を特定できないままレビューを完了扱いにしない。

作業条件と差分の保存先はレビュー対象ツリーの外に置く。統括の持つ会話やsystem promptが子へ継承されることに依存しない。

## 2. 探索役へ明示した依頼文を渡す

[実行環境別の渡し方](references/dispatch.md)を、使用する環境について読む。

各依頼文は次のスクリプトで作る。`SKILL_DIR` はこのスキルの絶対パスに置き換える。出力をUTF-8文字列として読み、子への依頼本文にそのまま渡す。

```bash
python3 SKILL_DIR/scripts/render_prompt.py --context /tmp/review-context.md --role finder --angle line-scan > /tmp/finder-line-scan.md
```

| angle | 探索する観点 |
| --- | --- |
| line-scan | 差分と周辺関数の逐行確認 |
| removed-behavior | 削除・置換された振る舞い |
| cross-file | 呼び出し元・先との整合 |
| reuse | 既存処理の再利用 |
| simplification | 状態・分岐・重複の単純化 |
| efficiency | 計算・I/O・待ち・メモリ保持 |
| altitude | 修正箇所と抽象化の粒度 |
| conventions | 適用規約への明確な違反 |

既定では1観点を1人へ割り当てる。観点の省略・統合や割り当ての変更は統括が理由とともに明示する。統合した観点は `--angle line-scan --angle cross-file` のように、`--angle` を繰り返して指定する。子が独自に再分担することは認めない。複数モデルで独立レビューするときは同じ対象・作業条件を渡し、互いの候補や結論を見せない。

子には作業条件の全文、担当観点、同じ対象を読める情報を渡す。差分を本文に含めずファイルを参照させる場合は、アクセス可能な固定スナップショットの絶対パスを作業条件に含める。

## 3. 候補を統合し、別の役へ検証を割り当てる

全探索役の完了・失敗を受け取ってから判断する。各候補は `(呼び出しID, 子が付けた候補ID)` で識別する。統括が一意な正規IDを割り当て、同じ原因と影響の候補を統合するときも元の組を別名として残す。既存指摘と同じ主張で新しい発生条件や根拠がなければ、新規候補へ格上げせず「既存指摘との一致」として短く残し、既存処分を適用する。実装変更を見ていないという理由で、既存処分を無条件に再審査しない。

残った候補を、発見者とは別の検証役へ1件ずつ渡す。統括がまとめ検証を指定した場合は、候補ごとの判定が返るよう明示する。
まとめ検証では、正規IDを付けた候補ブロックを1本のUTF-8ファイルへ連結し、既存の `--candidate` 引数で渡す。

```bash
python3 SKILL_DIR/scripts/render_prompt.py --context /tmp/review-context.md --role verifier --candidate /tmp/candidate-C1.md > /tmp/verifier-C1.md
```

検証役は技術的な主張について `CONFIRMED / PLAUSIBLE / REFUTED` と根拠を返し、対象・受け入れ基準への適用可否と既存処分を別に示す。対象外という理由だけで、成立する技術的主張を `REFUTED` にしない。`PLAUSIBLE` は未確認事項が残ることを表し、それだけで修正必須にしない。検証結果と受け入れ基準に基づき、統括が採用・非採用・追加確認を決める。既存指摘の処分を変えるときは、新しい根拠を示す。

不足した確認があれば子は統括へ返す。追加の探索や再現実行を誰に許可するかは統括が決める。検証役が補助役を連鎖的に起動すること、拒否された操作を別の役に委譲して実行することは認めない。

## 4. 制御と完了を確認する

開始時と同じ対象をレビューできたか、指定した役が実行されたか、作業条件が各依頼文へ渡ったかを確認する。対象が変わったら、その結果は元の対象への結果として扱う。現在の対象に適用して完了やGOを出さない。

対象・作業条件・指摘処分が変わらない限り、同じ検査やレビューを繰り返さない。失敗は指摘ゼロと区別する。必要な観点が未実行、採否に必要な候補が未検証、または実行上限に達した場合は、取得済み結果と未完了の箇所を返す。機能不足を隠して「独立レビュー完了」としない。

最終結果には次を含める。

- 固定した対象、実行した観点・モデルと effort、完了状況。
- 採用する指摘とその根拠、既存指摘との一致、既存処分を適用した指摘、新しい根拠で処分を変えた指摘。
- 未確認事項と制約。詳細表示を絞っても、採否に関わる候補を隠さない。
- 初回、再試行、修正後を含む実測時間・報告された消費。要求設定と観測設定、未計測とゼロを区別する。

レビューはコード変更・commit・push・投稿・公開の承認を兼ねない。GOが必要な場合も、呼び出し元の受け入れ基準と既存ゲートに対する判定として返す。
